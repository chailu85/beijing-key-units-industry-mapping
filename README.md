# Beijing Key Units Industry Mapping

> **421 重点行业分类统计**（“421”指国务院令第421号《企业事业单位内部治安保卫条例》）
> **Repository:** <https://github.com/chailu85/beijing-key-units-industry-mapping>

Conditional mapping of Beijing's 13 categories of key units under DB11/T 2552—2026 to China's national industry classification GB/T 4754—2017, supporting candidate screening, industry coding and statistical grouping.

本仓库把**治安保卫法规标准**里的重点单位类别，与**国民经济行业分类**做条件性对照，用于候选单位检索、行业归类和统计分组。

**版本（Releases）：** [v1](https://github.com/chailu85/beijing-key-units-industry-mapping/releases/tag/v1) ｜ [v2](https://github.com/chailu85/beijing-key-units-industry-mapping/releases/tag/v2) ｜ [v3](https://github.com/chailu85/beijing-key-units-industry-mapping/releases/tag/v3) ｜ [v3.1（现行版）](https://github.com/chailu85/beijing-key-units-industry-mapping/releases/tag/v3.1)

两条法律依据侧：**《企业事业单位内部治安保卫条例》（国务院令第421号）** 与北京市地标 **DB11/T 2552—2026《单位内部安全防范通用要求》第6.1条**（13 类重点单位，编号 a—m；n 项为兜底条款，不单列为第14类）。分类侧：《国民经济行业分类》**GB/T 4754—2017**（按第1号修改单修订）。数据侧：天眼查 `tyc` CLI 拉取的企业明细。

> 中文名中的“421”即国务院令第421号，具体依据见现行版 [S4] 条款。

## 核心结论（决定了所有文档的写法）

1. **不是一一对应。** 第6.1条划分的是治安保卫重点单位**类别**，GB/T 4754 划分的是**主要经济活动**，两者维度不同。因此全部对照都是"条件性对照"，任何代码清单都不构成穷尽清单，也不因代码相同便获得相同的重点单位身份。
2. **对应关系分两层映射＋两项限定。** 映射＝常见对应／条件对应；限定＝行业内需限定的范围／资格或属性条件。四者不同层级，不能用"条件对应"四个字解决范围问题。
3. **确定依据与属性证明分列。** 重点单位确定依据（公安机关提出、报本级政府确定的文件）与业务属性证明（名录、批复、许可证、资质证书）分别记录，后者不单独替代前者。
4. **行业代码不是可机械展开的区间。** 651 中类下只有 6511／6512／6513／6519（无 6514—6518），745 中类下只有 7451—7455、7459（无 7456—7458）。检索须按官方字典逐码展开；这条已写成执行规则并有校验脚本兜底。
5. **缺少纳入理由的行业直接剔除。** 若某代码只能解释"怎么编码"、说不出"为何属于第6.1条对象"（服务提供者、中介、管理机关、上游业务），不靠在表里加注"条件对应"取得纳入资格，一律移入"附：易混淆活动"。

## 文件命名规则

`docs/` 下两类文件，一套规则：

```
{系列名}_v{版本}_{日期}.md                # 对照表本体（一版一文件，不覆盖）
{系列名}_{文件性质}_第{轮次}轮_{日期}.md   # 审查意见（第1轮、第2轮…）
```

- **系列名固定**为 `重点单位13类_GBT4754-2017条件性对照`，系列各版共用，`ls docs/archive` 能按版本聚在一起，跨版本 diff 也只需比版本号。
- **版本号与复核日期**：`v1` 对应 2026-07-18，`v2`、`v3`、`v3.1` 对应 2026-10-28（取文内 `reviewed` 字段）。v1 文内标题没有版本号，按此规则补 `_v1_20260718`；v3.1 表示在v3框架内完成的内部一致性修正。
- **审查意见用“轮次”而不是版本号**：第 1 轮审 v1（产出 v2），第 2 轮复审 v2（产出 v3）。意见不是版本，是版本的输入，所以不进 `_vN_` 序列。
- 不用“最终”“定稿”“new”“修订版”“副本”这类词；**现行与否只看位置**——在 `docs/` 根部就是现行，在 `archive/` 就是历史。
- 技术笔记（如 `tyc-cli-查询模式.md`）不是成文文件，不参与版本命名，保留 `{主题}-{类型}.md` 的短名。

## 数据口径

| 数据 | 来源 | 用途 |
|---|---|---|
| 分行业法人单位数 | 北京市第五次全国经济普查（2023 年末） | 各行业门类总量与占比基准 |
| 重点行业企业明细 | 天眼查 `tyc` CLI | 按行业代码 + 地区代码拉取企业清单，作重点行业样本 |

- 地区代码：北京市 `00110101`（`areaCode`）
- 行业代码：GB/T 4754 **纯数字码**，如 `44`（大类）、`4420`（小类）；写成 `D44` 会直接返回空结果
- 企业接口只覆盖企业主体，机关、团体、事业单位、民办非企业需另接名录——代码表无法弥补主体覆盖缺口

## 常用命令

```bash
# 天眼查自检
tyc --version

# 按行业 + 地区拉企业清单（示例：北京市电力供应业）
tyc company companies-by-industry-region "电力" \
  --industry "4420" --region "00110101" \
  --pageNum 1 --pageSize 50 --md

# 核验现行对照表中所有行业代码（默认核 v3.1）
python tools/check_codes.py
python tools/check_codes.py "docs/archive/重点单位13类_GBT4754-2017条件性对照_v2_20261028.md"
```

更多查询模式、代码格式陷阱与配额规则见 [docs/tyc-cli-查询模式.md](docs/tyc-cli-查询模式.md)。

## 复现与校验

- `ref/code_entries.json` 是官方《2017国民经济行业分类注释》的代码字典（代码／名称／包含排除注释），已入库，`check_codes.py` 依赖它。
- `ref/` 下的 PDF 与 XLSX 受版权保护、体积较大，**不入库**。重新获取地址见现行版文档第八部分 [S1]（DB11/T 2552）、[S2]（GB/T 4754）、[S3]（分类注释 XLSX）。放回 `ref/` 后可用 `python tools/check_codes.py --rebuild` 重建字典（该步需 `openpyxl`，日常校验不需要）。
- 校验脚本的判定：文档中出现的 4 位小类／2 位大类若在字典中查不到即报错；`tools/known_absent.txt` 中登记的代码（6514／6518／7456／7458，用于说明"区间不可展开"）视为预期，不计错。URL 中的数字片段不参与校验。

## 工作约定

1. 天眼查拉取结果落盘 `data/`，文件名 `{地区}{行业}_{数据源}.csv`；UTF-8 with BOM，字段顺序固定，便于跨版本 diff。
2. 文档按上文“文件命名规则”：现行版在 `docs/` 根部，被取代版本进 `docs/archive/`，审查意见进 `docs/archive/reviews/`；改名或升版时同步更新 front-matter 的 `series`／`supersedes`／`audit_basis` 与本 README 的“版本与名称关系”表。
3. 每次数据更新在提交信息中注明数据月份与拉取口径。
4. 临时抽取产物、PDF 文本、上传回执一律不进仓库（`tmp/` 已在 `.gitignore`）。
